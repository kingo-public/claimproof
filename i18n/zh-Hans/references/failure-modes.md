# 九种失效模式

下面每一种模式都产生过一份**自信的假报告**，而且它通过了当时所有的检查。它们按形态分组，不按领域——同一种形态会在测试、部署、CSS、配置和散文里反复出现。

每条包含：*形态*、*它如何出现*，以及*一个带数字的真实案例*。

---

## 1. 设置不等于测量

**形态。**一个配置值、环境变量或声明的意图，被当作对行为的观察来读取。

**它如何出现。**
- "超时被设成了 5s" 被报告成 "请求在 5s 时超时"
- 配置说该功能是关闭的，被报告成 "该功能是关闭的"
- 一个名为 `currentVersion` 的变量被当作实际提供的版本

**真实案例——从未被加载的配置。**
> 一个浸泡测试把它要测的目标目录写进配置，作为 `SOAK_DIR`。报告从那份配置里读取构建标识，并据此断定这次运行检验的是预期的构建。而浏览器实际上加载的是*官方*发布版。所有 **71** 次观察到的失败，测量的都是错误的产物。修复方式是比对**实际提供内容的哈希**，而不是那个本该产生它的设置。

**修复。**把"我设了 X"换成"我观察到 Y，而 Y 是从我在意的东西推导出来的"。尽可能让设置和测量成为*同一个对象*：从文件哈希推导出缓存失效标记，而不是手工维护一个版本号。那样就没有任何数字可以被忘记。

## 2. 没有正向对照

**形态。**一个检测器报告了干净的结果，但从未被证明能够检测到脏的结果。

**它如何出现。**
- 一份零数据包的抓包结果被读成"没有发出任何东西"
- 一个什么都不打印的监视器被读成"没有问题"
- 一个返回 `null` 的探针被读成"有风险的路径被避开了"

**真实案例 A——漏掉 IPv6 的过滤器。**
> 一次抓包按一份地址列表过滤，而那份列表漏掉了一个 IPv6 网段。`curl https://google.com` 成功了，而抓包报告 **0 个数据包**。"没有流量离开这台机器"这个结论，差一点就是从这样一个过滤器得出的——它从结构上就看不见它所针对的那类流量。一个正向对照——抓一个已知会经过那个网络的请求——本可以立刻揭穿它。

**真实案例 B——用错全局变量的探针。**
> 一个探针检查 `window.__uploadConsent` 来判断某个同意门是否处于激活状态。真正的全局变量叫另一个名字，所以那次查找永远是 `undefined`。探针报告"同意门未被强制执行"——一个关于产品的警报，却完全由仪器造成。

**修复。**在信任任何否定结果之前，先拿一个你已经知道答案的案例来运行这个仪器。**没有正向对照的 `0` 不是证据。**

## 3. 没有负样本

**形态。**一个检查存在并且通过。从来没有什么东西让它失败过。你无法区分"它看了，没发现不对"和"它根本没在看"。

> "没有它，我只知道*检查通过了*。我不会知道*检查到底有没有在看*。"

**真实案例——一个永远无法触发的断言。**
> 一个 gate 承诺要验证页面标题是否包含某些关键词。它的表达式以一种构造上恒为真的方式比较了一个值。它在每一次运行中都报告 PASS，包括那些标题被故意清空的运行。这个 gate 已经绿了好几个星期，却从来没有测试过任何东西。

**修复。**每个检查都要附带一个故意写坏的样本，在同一次调用中运行。四种状态是一个好的默认设置：

```
product currently    -> PASS   (the real case)
title emptied        -> FAIL   (broken sample 1)
keyword removed      -> FAIL   (broken sample 2)
wrong attribute used -> FAIL   (broken sample 3)
```

**一个仅仅因为没有东西弄坏它而通过的检查，是你从未运行过的检查。**

## 4. 绿灯不等于正确

**形态。**一个信号证明了一个属性，却被读成证明了另一个属性。

| 信号 | 实际证明 | 常被读成 |
| --- | --- | --- |
| `HTTP 200` | 服务器可达 | 提供的内容是对的 |
| `syntax OK` | 文件可解析 | 代码在履行它的职责 |
| `deploy exited 0` | 复制命令跑了 | 用户现在拿到新版本了 |
| `tests passed` | 有东西断言成功了 | 被测试的是对的东西 |
| `file exists` | 某个路径被占用了 | 内容就是你写的东西 |

**真实案例 A——看不见内联脚本的 lint。**
> `php -l` 验证 PHP，并且**对内联脚本块视而不见**。内联脚本里的一个 JavaScript 语法错误，意味着整个页面的 JS 都是死的。linter 是绿的，响应是 `HTTP 200`，页面渲染了。什么都没错，除了一切都坏了。

**真实案例 B——证明双方都已过期的哈希相符。**
> 一个构建产物和它的镜像的哈希**完全相同**。这被报告成"改动已经上线"。随后运行内容断言，三条全部失败。那个产物比那次编辑**早了 32 秒**。产物和镜像之所以彼此相符，*是因为它们是一起过期的。*哈希比对**从构造上就不可能检测出双方都已过期**——它们就是同一个文件。

**真实案例 C——手工维护的版本号。**
> 一次 CSS 改动上线了，却没有更新硬编码的版本标记。用户拿到的是新 HTML 配旧样式表。这次部署在所有可用的信号上都是成功的。

**修复。**把你在意的属性单独断言出来。HTTP 200 **并且**是预期的字节。语法有效**并且**那个函数仍然能执行。已部署**并且**实际提供的哈希变了。

## 5. 把弱关系当强关系卖

**形态。**一个回答更弱问题的关系，被用在需要更强关系的地方。这个弱关系不仅仅是精度更低——在面对相反的输入时，它会给出**相反的答案**。

| 弱关系 | 被读成 | 看不见 |
| --- | --- | --- |
| `a != b` | "a 更新" | 哪一边更新 |
| `prefix(l, 46)` | "同一个标识符" | 两行共享同一个前缀 |
| `substring present` | "内容在里面" | 内容被移到别处了 |
| `timestamp set` | "这是新鲜的" | 新鲜度 |
| `grep found keyword` | "这个功能存在" | 一条提到它的注释 |

**真实案例 A——反了的比较。**
> 一个过期检查用 `!==` 比较三个时间戳，报告"有一个更新的版本"。`!==` 只知道*不同*，不知道*更新*。当那个新值实际上**更旧**时，这个检查自信地报告了相反的结果。什么都没崩。页面返回 200，所有数字看起来都合理，而**没有任何 gate 亮起来。**它只是靠把三个时间戳并排打印出来才被发现。这一行代码是**七个**用户可见输出的闸门。修*比较*，七个全修好了；修*措辞*，则需要改七处，而且 bug 还留在原地。

**真实案例 B——前缀碰撞。**
> 恢复文件时，各行以前 46 个字符作为键。来自同一路径的两行共享了同一个 46 字符前缀，于是一行静默地覆盖了另一行。输出自豪地报告"恢复了 30 行"——这句话是真的，也是错的。

**真实案例 C——数到注释的 grep。**
> 用 `grep -o '!important'` 来统计声明数量。它数出 **298**；真实数字是 **291**。它匹配到了源码注释和文档里的出现。这个模式出现在了*描述*这个模式的代码里。

**修复。**问问这个弱关系在*相反*输入上会怎样。如果它给出的是一个自信的错误答案，而不是没有答案，那它就是错的关系。用位置或完整内容来做身份标识。用 `>` 来排序。匹配渲染后的文本来判断内容，而不是源码文本。

## 6. 量错了对象

**形态。**A 的一个属性被用作 B 某个属性的代理。这个代理在静默地停止追踪之前，都是合理的。

**它如何出现。**
- 当可点击区域是一个伪元素时，去测量元素自身的盒子
- 当可见性取决于视口时，去测量容器的边界
- 当问题是服务器提供什么时，去测量磁盘上的文件
- 标签说的是字符时去测量字节，或者反过来

**真实案例 A——不是元素本身的可点击区域。**
> 触摸目标尺寸是在锚元素自身上测量的。实际的可点击区域来自一个绝对定位、覆盖在它上面的伪元素。测量的是错误的矩形，并且让一个实际上达标的控件没能通过无障碍检查。

**真实案例 B——不是视口的容器。**
> 通过把元素边界与一个*滚动容器*比较，判定内容被"裁剪"了。那些元素是固定定位的，而且在屏幕上是完全可见的。测量容器产生了系统性的误报——这是那天第四起"拿 A 的属性来代表 B"。

**真实案例 C——被冻结的动画。**
> 在一个动画播放到中途的元素上测量了边界矩形，并把它当成该元素的布局位置来报告。每一次读数都只是一个瞬间，不是一个位置。更糟的是：用带 `!important` 的通用选择器尝试冻结，对上一个本身就是 `!important` 的动画时**并不管用**，因为通用选择器的优先级是 (0,0,0)，会输给一个类选择器 (0,1,0)。这次冻结被断言为"完成"，却没有被验证为"有效"。

**修复。**在测量之前先问：*这个数字对应的是用户实际体验到的东西吗？*把这种对应关系明确说出来。涉及两个对象时，两个都测，并报告它们之间的差距。

## 7. 把沉默读成成功

**形态。**一个错误被吞掉了，于是"仪器坏了"表现为"一切正常"。

```
// turns "my probe is broken" into "the system is clean"
child.on('error', () => {});
await doThing().catch(() => {});
```

**真实案例——端口已经被占了。**
> 一个测试框架绑定了一个**固定端口**，并挂上了一个空的错误处理器。上一次运行遗留下来的一个服务器已经占着这个端口。启动*静默地*失败了；测试框架连上了那个旧服务器，提供的是错误的目录。整个运行——**71** 次失败的观察——测量的产物和被测代码毫无关系。

**修复。**永远不要吞。当一个结果是"全部失败"或"零观察"时，你的第一个问题是：

> **这个零，是我的仪器造成的，还是被测对象造成的？如果我分不清，那就是我的仪器没有报告它自己的失败——先修仪器。**

## 8. 没人运行的 gate 不是 gate

**形态。**一个检查存在于仓库里，是正确的，而且从未被调用。

**它如何出现。**
- 一个写好了但从未接入 CI 或定时器的脚本
- 一个已定义但启动路径缺少执行权限位的定时器
- 文档里承诺的"自检"，代码里根本不存在

**真实案例——活在规则手册里的承诺。**
> 一份约定文件声称某个检查器附带"六个对照用例"。那个检查器里根本没有自检。这个说法在有人注意到之前，已经被复制进了三个备份文件。**这个承诺活在规则文件本身上**——那份所有人都信任、用来描述现实的文件。

**修复。**对每一个检查都回答：*如果没人记得去运行它，它还会运行吗？*如果不会，那它就是一条注释。把静态检查接到定时器上；把动态检查接到会让它变得相关的那次改动上。然后通过**等它触发一次**来验证这套接线——一个已声明的定时器是设置，不是观察。

## 9. 错误的 gate 比没有 gate 更糟

**形态。**一个检查对正确的工作报告失败。它训练人们忽略它，并派人去修那些从来没坏过的东西。

**真实案例 A——SIGPIPE 被误读为失败。**
```
set -o pipefail
curl -s "$url" | grep -q "expected"    # reports FAILURE on success
```
> `grep -q` 一匹配就退出。`curl` 收到 SIGPIPE，以退出码 141 死掉。`pipefail` 把它作为失败向上传播。于是这个检查对一个提供的正是预期内容的页面报告了失败。**修复：先把响应写进文件，然后对文件 grep。没有管道，就没有 SIGPIPE。**

**真实案例 B——把退出码当作值用。**
```
code=$(... | grep -c X || echo 0)     # prints TWO zeroes when not found
[ "$code" = "0" ]                     # fails: two zeroes != one zero
```
> 正确的工作又一次被报告成坏的。修复方式是把值从退出状态里分离出来。

**修复。**当你为了让一个误报闭嘴而放宽规则时，你必须加一个**逃生舱样本**——一个故意写坏的输入，证明放宽后的规则仍然抓得住真正的违规。**没有它，"放宽了"和"删掉了"看起来一模一样。**

## 横切关注点：从未执行过的失败路径

它本身不是一种模式，而是模式 3、8、9 持续存在的原因：

> 成功路径每天都在跑。失败路径可能**一次都没跑过**——而失败路径正是这个检查存在的全部理由。

跑一次。手工，故意。然后把你跑了这件事记录下来。

## 如何使用本文档

当你即将报告成功时，扫一遍这九种形态：

1. 我是不是在把设置当测量报告？
2. 我的仪器见过一个已知为阳性的案例吗？
3. 我的检查曾经变红过吗？
4. 我的绿色信号能证明我声称的那个属性吗？
5. 有没有哪个比较弱于它所要回答的问题？
6. 我测量的是用户实际体验到的那个对象吗？
7. 在我和读数之间，有没有错误被静默吞掉了？
8. 我不在的时候，这个检查会运行吗？
9. 这个检查曾经喊过狼来了吗？
