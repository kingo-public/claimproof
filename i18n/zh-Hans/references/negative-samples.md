# 负样本

一个负样本是**喂给一个能正常工作的检查的、故意写坏的输入，用来证明这个检查能够变红。**

没有它，你无法区分两个截然不同的世界：

| 世界 | 你观察到什么 | 什么是真的 |
| --- | --- | --- |
| A | 检查通过 | 被测对象是正确的 |
| B | 检查通过 | **这个检查根本没在看任何东西** |

A 和 B 产生**完全相同的输出**。只有负样本能把它们分开。

## 1. 核心主张

> **一个从未失败过的检查，从未被证明检查过任何东西。**

这不是一个哲学论点。检查就是一个过滤器。一个什么都通过的过滤器，和一个没有过滤器无法区分。负样本就是你用来证明这个过滤器存在截断点的方式。

三种违反这一点的真实形态：

1. **同义反复。**一个把值与自身比较、或与一个使断言构造上恒为真的常量比较的断言。报告了数周的 PASS。
2. **自指的搜索。**一个文本搜索，它的模式也出现在它自己的注释里，或出现在描述旧行为的文档里。它匹配的是描述，不是那个东西。
3. **缺失功能检查。**一次重构删掉了功能 X。而那个检查只断言了"X 不存在"，所以它保持着绿色——现在它永远因为错误的理由而通过。

## 2. 什么算作负样本

负样本是任何**应该**让检查失败的输入。好的负样本：

- **内容清空。**把真实标题替换成空字符串。
- **顺序颠倒。**用错误的顺序给检查传值。
- **错误的标识符。**喂一个相似但不同的键。
- **移除元素。**删掉检查声称要找到的那个东西。
- **损坏的值。**引入一个细微的语法错误。
- **边界输入。**差一错误、空集合、单个元素。

糟糕的负样本（这些什么都证明不了）：

- 坏到让检查因为一个无关原因而失败的东西（崩溃、文件缺失）——你证明的是这个检查会报错，不是它能区分。
- 在与真实运行*不同的 session* 里跑的样本。
- 你写了但从未执行过的样本。

## 3. 四态协议

把四个状态**在同一次调用**里全部跑一遍，并打印全部四个结果：

```
STATE                EXPECTED   PURPOSE
product as-is        PASS       the real case
negative sample 1    FAIL       proves the check discriminates
negative sample 2    FAIL       proves it is not keyed to one property
restore product      PASS       proves the negative did not corrupt state
```

第四个状态比人们以为的更重要：它证明你观察到的那个失败来自你的样本，而不是运行检查带来的副作用。

### 例子：一个检查页面标题是否包含关键词的检查

```
input                        expected   observed
wc -c <<< "$title"  > 0      PASS       PASS      (real)
title=""                     FAIL       FAIL      (empty)
title="wrong text"           FAIL       FAIL      (no keywords)
title back to original       PASS       PASS      (restored)
```

在这个协议存在之前，这个检查在第 2 行上也报告 PASS——而那就是发现。

## 4. 特例：不可能失败的断言

这些是价值最高的负样本，因为这些断言看起来是健康的。症状：

- 同一个布尔常量出现在比较的两边；
- 被搜索的字符串出现在执行搜索的代码里；
- 检查测试的是代码无条件设置的一个属性；
- 计数器被封顶了，所以你丢弃 0 项还是 12 项，它都报告同一个值；
- 断言的标题所承诺的比表达式所测试的更多。

**断言的标题和它的表达式不一致，这本身就是个 bug。**标题是人读的东西；如果它过度承诺，这个检查就是一份说谎的文档。

## 5. 放宽检查，而不是删掉它

当一个检查喊狼来了时，诱人的修法是把它放松。做得不小心，"放松了"和"删掉了"就变成了同一件事。

**每一次放宽都需要一个逃生舱样本**：一个故意写坏的输入，证明*放宽后*的规则仍然抓得住真正的违规。

```
RULE (old, false-positive on legitimate work)   -> relax
REAL VIOLATION (must still fail)               -> proves the rule survives
FALSE POSITIVE (must now pass)                 -> proves the noise is gone
```

如果你构造不出"真正的违规"那一行，那你就不是放宽了规则，而是删掉了它。明确说出来，而不是留下一个看起来能工作的检查。

## 6. 常见错误

- **只在之前的一次运行里证明过一次。**上周建立的对照，是一句关于上周的话。在与声明同一个 session 里重新跑它。
- **共享同一个 bug 的负样本。**如果你的坏样本坏的方式和真实输入会坏的方式一样，它什么都证明不了。
- **测试 mock。**确认你的测试替身按写好的方式行为，而不是确认真实集成能工作。
- **把"检查失败了"和"检查能工作"搞混。**检查必须*在坏输入上失败、在好输入上通过*。只有其中一个，就是半个协议。
- **静默跳过。**一个因依赖缺失而被跳过的检查什么也不报告，而什么都不报告看起来就像成功。让跳过发出声音。

## 规则

> **每个检查都要附带一个故意写坏的样本，在同一次调用中运行，并打印结果。**

如果一个检查不可能有这样的样本，就说出来，并把它标记为 **UNVERIFIED**——不要让它报告 PASS，仿佛它已经被测试过。
