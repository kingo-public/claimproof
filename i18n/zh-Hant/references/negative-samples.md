# 負向樣本

負向樣本是一個**餵給正常檢查、故意寫壞的輸入，用來證明這個檢查能變紅。**

少了它，你無法區分兩個非常不同的世界：

| 世界 | 你觀察到什麼 | 什麼是真的 |
| --- | --- | --- |
| A | 檢查通過 | 受測對象是正確的 |
| B | 檢查通過 | **這個檢查根本沒在看任何東西** |

A 與 B 產出**完全相同的輸出**。只有一個負向樣本能把他們分開。

## 1. 核心主張

> **一個從未失敗過的檢查，從未被證明檢查過任何東西。**

這不是哲學觀點。一個檢查就是一個濾網。一個什麼都放行的濾網，與沒有濾網無法區分。負向樣本就是你證明這個濾網有截斷點的方式。

三種違反此事的真實形狀：

1. **套套邏輯。** 一個把值拿來跟它自己比較、或跟一個讓它在構造上恆為真的常數比較的斷言。回報 PASS 好幾週。
2. **自我指涉的搜尋。** 一個文字搜尋，它的 pattern 也出現在自己的註解裡，或出現在描述舊行為的文件裡。它 match 到的是描述，不是那個東西。
3. **缺席功能的檢查。** 一次重構刪掉了功能 X。這個檢查只斷言了「X 不存在」，所以它保持綠色——而現在它永遠因為錯誤的理由通過。

## 2. 什麼算是負向樣本

負向樣本是任何**應該**讓檢查失敗的輸入。好的負向樣本：

- **清空內容。** 把真正的標題換成空字串。
- **反轉順序。** 用錯誤的順序給檢查餵值。
- **錯誤的識別碼。** 餵一個相似但不同的鍵。
- **移除元素。** 刪掉那個檢查聲稱要找的東西。
- **損壞的值。** 引入一個微妙的語法錯誤。
- **邊界輸入。** off-by-one、空集合、單一元素。

壞的負向樣本（這些證明不了任何事）：

- 某個東西壞到讓檢查因為不相關的理由失敗（當掉、檔案不存在）——你證明的是這個檢查會出錯，不是它能分辨。
- 一個在與真實案例*不同 session* 中執行的樣本。
- 一個你寫了卻從未執行過的樣本。

## 3. 四態協定

四個狀態**都在同一次呼叫中**跑，並把四個結果都印出來：

```
STATE                EXPECTED   PURPOSE
product as-is        PASS       the real case
negative sample 1    FAIL       proves the check discriminates
negative sample 2    FAIL       proves it is not keyed to one property
restore product      PASS       proves the negative did not corrupt state
```

第四個狀態比人們預期的更重要：它證明你觀察到的失敗來自你的樣本，而不是來自執行這個檢查的副作用。

### 範例：一個檢查頁面標題是否包含關鍵字的檢查

```
input                        expected   observed
wc -c <<< "$title"  > 0      PASS       PASS      (real)
title=""                     FAIL       FAIL      (empty)
title="wrong text"           FAIL       FAIL      (no keywords)
title back to original       PASS       PASS      (restored)
```

在這個協定存在之前，這個檢查在第 2 列也回報 PASS——那正是當時的發現。

## 4. 特例：不可能失敗的斷言

這些是價值最高的負向樣本，因為這些斷言看起來很健康。徵狀：

- 同一個布林常數出現在比較的兩邊；
- 被搜尋的字串出現在執行搜尋的那段程式碼裡；
- 這個檢查測試的是一個程式碼無條件設定的屬性；
- 計數器有上限，所以不管你漏掉 0 筆還是 12 筆，它都回報同一個值；
- 斷言的標題承諾得比它表達式實際測試的還多。

**斷言的標題與其表達式之間的不一致，本身就是一個 bug。** 標題是給人讀的；如果它過度宣稱，這個檢查就是一份說謊的文件。

## 5. 放寬一個檢查，而不刪掉它

當一個檢查狼來了，誘人的修法是把它放寬。做得不小心，「放寬」與「刪除」就變成同一件事。

**每一次放寬都需要一個逃生艙樣本**：一個故意寫壞的輸入，證明*放寬後*的規則仍能抓到真正的違規。

```
RULE (old, false-positive on legitimate work)   -> relax
REAL VIOLATION (must still fail)               -> proves the rule survives
FALSE POSITIVE (must now pass)                 -> proves the noise is gone
```

如果你建構不出「真正的違規」那一列，你就不是放寬了規則；你是移除了它。明確說出來，而不是留下一條看起來能運作的檢查。

## 6. 常見錯誤

- **在先前某次執行中證明過一次。** 上週建立的對照，是一則關於上週的宣稱。要在與宣稱同一個 session 中重新跑它。
- **一個與 bug 共用同一個問題的負向樣本。** 如果你寫壞的樣本，壞的方式和真實輸入會壞的方式一樣，它就證明不了任何新東西。
- **測試 mock。** 確認你的測試替身照著寫的方式運作，而不是確認真正的整合能動。
- **把「檢查失敗了」與「檢查能運作」搞混。** 這個檢查必須在壞掉的輸入上失敗，*並且在好的輸入上通過*。只有其中一個，就是半套協定。
- **無聲的跳過。** 一個因為缺少相依性而被跳過的檢查什麼都不會回報，而什麼都不回報看起來就像成功。讓跳過這件事大聲說出來。

---

## 規則

> **每個檢查都隨附一個故意寫壞的樣本，在同一次呼叫中執行，並印出結果。**

如果一個檢查不可能有這種樣本，就說出來並把它標為 **UNVERIFIED**——不要讓它回報 PASS，彷彿它已經被測試過。
