# 九種失敗模式

以下每一種模式都曾產出一份**自信的、錯誤的報告**，而且通過了所有既有的檢查。它們是按**形狀**分組，不是按領域——同樣的形狀會在測試、部署、CSS、設定檔與文章中反覆出現。

每一則包含：*形狀*、*它如何出現*，以及*一個附數字的真實案例*。

---

## 1. 設定不等於量測

**形狀。** 一個設定值、環境變數或已宣告的意圖，被讀回來當成對行為的觀察。

**它如何出現。**
- 「timeout 設為 5s」被回報成「請求在 5s 時 timeout」
- 設定檔說該功能是關的，被回報成「該功能是關的」
- 一個名為 `currentVersion` 的變數，被當成實際送出的版本信任

**真實案例——那個從未被載入的設定檔。**
> 一次 soak test 把它的目標目錄寫進設定檔裡的 `SOAK_DIR`。
> 報告從那個設定檔讀取 build 識別碼，並據此認定這次執行
> 測到了預期的 build。事實上瀏覽器載入的是*官方*發行版。
> 所有 **71** 筆觀察到的失敗，都是在量測錯誤的產物。
> 修法是比對**實際送出內容的雜湊**，而不是比對那個
> 理應產生它的設定值。

**修法。** 把「我設定了 X」換成「我觀察到 Y，而 Y 是從我在意的那個東西推導出來的」。可能的話，讓設定與量測**成為同一個物件**：從檔案雜湊推導 cache-busting token，而不是手工維護一個版號。這樣就沒有數字可以忘記更新了。

## 2. 沒有正向對照

**形狀。** 一個偵測器回報乾淨的結果，但從未被證明能偵測出骯髒的結果。

**它如何出現。**
- 一份零封包擷取被讀成「沒有任何東西送出」
- 一個什麼都沒印的監控被讀成「沒有問題」
- 一支回傳 `null` 的探針被讀成「已避開有風險的路徑」

**真實案例 A——漏掉 IPv6 的濾網。**
> 一份封包擷取過濾在一個位址清單上，而那個清單漏掉了一段 IPv6 範圍。
> `curl https://google.com` 成功了，而擷取卻回報
> **0 個封包**。「沒有任何流量離開這台機器」這個結論，差點就
> 從一個在結構上就對該流量視而不見的濾網推導出來。一個
> 正向對照——擷取一個已知會經過該網路的請求——本來可以
> 立刻揭穿它。

**真實案例 B——用錯全域變數的探針。**
> 一支探針檢查 `window.__uploadConsent` 來判斷某個同意
> 閘門是否啟用。真正的全域變數名稱不同，所以查詢永遠是
> `undefined`。這支探針回報「同意閘門未強制執行」——
> 一個關於產品的警報，完全由儀器造成。

**修法。** 在信任任何負向結果之前，拿儀器去跑一個你已經知道答案的案例。**一個沒有正向對照的 `0`，不是證據。**

## 3. 沒有負向樣本

**形狀。** 一個檢查存在且通過。從沒有任何東西讓它失敗過。你無法分辨「它看過了、沒發現問題」與「它根本沒在看」。

> 「少了它，我只會知道*這個檢查通過了*。我不會知道
> *這個檢查到底有沒有在看*。」

**真實案例——那個永遠不可能觸發的斷言。**
> 一個閘門號稱能驗證頁面標題包含某些關鍵字。它的
> 表達式用一種在構造上恆為真的方式比較一個值。它
> 在每一次執行都回報 PASS，包括標題被
> 故意清空的那幾次。這個閘門綠了好幾週，卻從未測試過
> 任何東西。

**修法。** 每個檢查都隨附一個故意寫壞的樣本，在同一支呼叫中執行。四個狀態是不錯的預設：

```
product currently    -> PASS   (the real case)
title emptied        -> FAIL   (broken sample 1)
keyword removed      -> FAIL   (broken sample 2)
wrong attribute used -> FAIL   (broken sample 3)
```

**一個只因為沒人去弄壞它才通過的檢查，是一個你還沒跑過的檢查。**

## 4. 綠燈不等於正確

**形狀。** 一個訊號證明了一項性質，卻被讀成證明了另一項。

| 訊號 | 實際證明的 | 常被讀成 |
| --- | --- | --- |
| `HTTP 200` | 伺服器可達 | 送出的是正確內容 |
| `syntax OK` | 檔案可解析 | 程式碼有發揮作用 |
| `deploy exited 0` | 複製指令有跑 | 使用者現在拿到新版本 |
| `tests passed` | 有東西斷言成功了 | 測到的是對的東西 |
| `file exists` | 路徑被佔用 | 內容是你寫的那個 |

**真實案例 A——看不見行內 script 的 lint。**
> `php -l` 驗證 PHP，而且**對行內 script 區塊視而不見**。行內 script
> 裡的一個 JavaScript 語法錯誤，讓整個頁面的 JS 全部
> 死掉。linter 是綠的、回應是 `HTTP 200`、頁面
> 也渲染出來了。什麼都沒錯，除了全部都是壞的。

**真實案例 B——證明兩邊都過期的雜湊相符。**
> 一個 build 產物與它的鏡像有**完全相同的雜湊**。這被回報成
> 「變更已經上線」。接著內容斷言跑了，三項全數失敗。那個
> 產物比這次編輯**早了 32 秒**。產物與鏡像
> 彼此相符，*因為它們一起過期了。* 雜湊
> 比對**在構造上就無法偵測出兩邊都已過期**——
> 它們是同一個檔案。

**真實案例 C——手工維護的版號。**
> 一次 CSS 變更上線了，卻沒有更新一個寫死的版號 token。使用者
> 收到新的 HTML 配上舊的樣式表。以每一個
> 可用的訊號來看，這次部署都成功了。

**修法。** 分別斷言你真正在意的那項性質。HTTP 200 **而且**位元組如預期。語法有效**而且**函式仍能執行。已部署**而且**實際送出的雜湊變了。

## 5. 弱關係當成強關係賣

**形狀。** 一個只能回答較弱問題的關係，被用在需要較強關係的地方。這個弱關係不只是不夠精確——在相反的輸入上，它會給出**相反的答案**。

| 弱關係 | 被讀成 | 看不見什麼 |
| --- | --- | --- |
| `a != b` | 「a 比較新」 | 哪一邊比較新 |
| `prefix(l, 46)` | 「同一個識別碼」 | 兩列共用同一個前綴 |
| `substring present` | 「內容就在那裡」 | 內容被搬到別的地方 |
| `timestamp set` | 「這是新鮮的」 | 新鮮度 |
| `grep found keyword` | 「該功能存在」 | 一段提到它的註解 |

**真實案例 A——反向的比較。**
> 一個 staleness 檢查用 `!==` 比較三個時間戳，回報
> 「有更新的版本」。`!==` 只知道*不同*，不知道
> *更新*。當新值實際上**更舊**時，這個檢查自信地
> 回報了相反的結果。什麼都沒當掉。頁面回傳 200、數字全
> 看起來合理，而且**沒有任何閘門亮燈。** 它是靠把三個
> 時間戳並排印出來才被發現的。
> 那一行程式碼把關了**七個**使用者可見的輸出。修好*比較*，
> 七個全數修正；修*措辭*則需要改七個地方，而且
> 會把 bug 留在原地。

**真實案例 B——前綴碰撞。**
> 還原檔案時，每一列以其前 46 個字元作為鍵。同一路徑的
> 兩列共用了 46 字元的前綴，所以其中一列悄悄覆蓋了
> 另一列。輸出還得意地回報「還原了 30 列」——這是真的，也是
> 錯的。

**真實案例 C——把註解也算進去的 grep。**
> `grep -o '!important'` 被用來計算宣告數量。它算出
> **298**；真正的數字是 **291**。它 match 到了原始碼
> 註解與文件裡的出現。這個 pattern 就出現在*描述*
> 這個 pattern 的程式碼裡。

**修法。** 問問這個弱關係在*相反*的輸入上會怎樣。如果它給出的是自信的錯誤答案、而不是沒有答案，那它就是錯的關係。用位置或完整內容來判斷身分。用 `>` 來判斷順序。要用渲染後的文字來比對內容，不是原始碼文字。

## 6. 量錯對象

**形狀。** 拿 A 的屬性當作 B 的屬性的代理。這個代理在它悄悄停止追蹤之前，看起來都還算合理。

**它如何出現。**
- 量元素自己的 box，但可點擊區域其實是偽元素
- 量容器的邊界，但可見性取決於 viewport
- 量磁碟上的檔案，但問題是伺服器實際送出什麼
- 量位元組，但標籤寫的是字元，或反過來

**真實案例 A——不是元素本身的可點擊區域。**
> 觸控目標大小是量在錨點元素本身。真正的
> 可點擊區域來自一個絕對定位、覆蓋它的偽元素。
> 量到的是錯誤的矩形，於是讓一個實際上符合標準的
> 控制項在無障礙檢查中失敗。

**真實案例 B——不是 viewport 的容器。**
> 內容被判定為「被裁切」，做法是把元素邊界拿去和一個*捲動
> 容器*比較。那些元素是 fixed 定位，在螢幕上完全可見。
> 量容器產生了系統性的偽陽性——這是當天第四次
> 「拿 A 的屬性去代表 B」。

**真實案例 C——被凍結的動畫。**
> 一個邊界矩形是在元素動畫進行中量到的，卻被回報成
> 它的版面位置。每一次讀數都是一個瞬間，不是一個位置。更糟的是：
> 那次嘗試用通用選擇器加 `!important` 來凍結動畫，**行
> 不通**，因為那個動畫自己也是 `!important`——
> 通用選擇器的 specificity 是 (0,0,0)，會輸給 class 的 (0,1,0)。
> 這次凍結被宣稱「完成」，卻沒有被驗證是否「有效」。

**修法。** 量測之前先問：*這個數字對應到使用者實際體驗到的東西嗎？* 把對應關係明確說出來。涉及兩個物件時，兩個都量，並回報落差。

## 7. 把沉默讀成成功

**形狀。** 錯誤被吞掉，所以「儀器壞了」表現成「一切正常」。

```
// turns "my probe is broken" into "the system is clean"
child.on('error', () => {});
await doThing().catch(() => {});
```

**真實案例——已經被佔用的埠。**
> 一個測試框架綁定一個**固定埠**，並掛上空的錯誤處理器。上一次
> 執行遺留的伺服器還佔著那個埠。啟動*無聲地*失敗了；
> 框架連上了那個舊伺服器，送出了錯誤的目錄。整次執行——
> **71** 筆失敗觀察——量到了一個與受測程式碼
> 毫無關係的產物。

**修法。** 絕不吞掉。當結果是「全部失敗」或「零觀察」時，你的第一個問題是：

> **這個零，是我的儀器造成的，還是受測對象造成的？
> 如果我分不出來，那就是我的儀器沒有回報自己的失敗——修
> 儀器。**

## 8. 沒人跑的閘門不是閘門

**形狀。** 一個檢查存在於 repo 裡、是正確的，而且從未被呼叫。

**它如何出現。**
- 一支寫好卻從未接上 CI 或排程的腳本
- 一個排程定義了，但它啟動的路徑少了執行權限位
- 文件裡承諾的一個「自我測試」，在程式碼裡根本不存在

**真實案例——活在規則手冊裡的承諾。**
> 一份慣例文件聲稱某支檢查器隨附「六個對照案例」。那支
> 檢查器根本沒有任何自我測試。這項說法在被任何人注意到之前，
> 已經被複製進三份備份檔案。**這個承諾就活在規則檔案
> 自己身上**——那是所有人信任、用來描述現實的文件。

**修法。** 對每個檢查回答：*如果沒有人記得跑它，它還會跑嗎？* 如果不會，它就是一段註解。把靜態檢查接上排程；把動態檢查接上那個讓它們變得相關的變更。然後用**等它觸發一次**來驗證接線——一個宣告的排程是設定，不是觀察。

## 9. 錯的閘門比沒有閘門更糟

**形狀。** 一個檢查對正確的工作回報失敗。它訓練人們忽略它，並叫人去修從來沒壞過的東西。

**真實案例 A——SIGPIPE 被誤讀為失敗。**
```
set -o pipefail
curl -s "$url" | grep -q "expected"    # reports FAILURE on success
```
> `grep -q` 一 match 到就立刻結束。`curl` 收到
> SIGPIPE，以 exit 141 死亡。`pipefail` 把它當成
> 失敗往外傳。這個檢查對一個送出完全符合預期內容的頁面
> 回報失敗。**修法：先把回應寫進檔案，再 grep 那個
> 檔案。沒有管線，就沒有 SIGPIPE。**

**真實案例 B——把離開碼當成值來用。**
```
code=$(... | grep -c X || echo 0)     # prints TWO zeroes when not found
[ "$code" = "0" ]                     # fails: two zeroes != one zero
```
> 正確的工作又被回報成壞的。修法是將這個值
> 與離開狀態分開。

**修法。** 當你為了消掉偽陽性而放寬一條規則時，你必須加上
一個**逃生艙樣本**——一個故意寫壞的輸入，證明放寬後的
規則仍能抓到真正的違規。**少了它，「放寬」與「移除」
看起來一模一樣。**

## 橫向議題：從未被執行過的失敗路徑

它不是獨立的一種模式，而是模式 3、8、9 之所以持續存在的原因：

> 成功路徑天天跑。失敗路徑可能**從來沒跑過
> 一次**——而失敗路徑正是這個檢查存在的全部理由。

去跑它。一次，手動，刻意地。然後記錄下你跑過了。

## 如何使用這份文件

當你即將回報成功時，掃過這九種形狀：

1. 我是不是把設定當成量測在回報？
2. 我的儀器見過已知為正的案例嗎？
3. 我的檢查曾經變紅過嗎？
4. 我的綠燈訊號證明了我正在宣稱的那項性質嗎？
5. 有沒有哪個比較比它要回答的問題更弱？
6. 我量的是使用者實際體驗到的那個對象嗎？
7. 在我與讀數之間，有沒有任何錯誤被悄悄吞掉？
8. 我不在的時候，這個檢查還會跑嗎？
9. 這個檢查曾經謊報過嗎？
